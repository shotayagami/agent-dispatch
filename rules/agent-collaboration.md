# Claude と Codex の協調ルール（サンプル）

Claude Code と Codex が同じリポジトリで作業するときの決まりです。

## 着手の宣言

- 複数のエージェントが関わる作業と、無人で起動した作業は、Issue を単位にする。
- 着手前に Issue のコメントを読む。別のエージェントの着手コメントが閉じられずに残っていれば、手を付けない。
- 着手するときは、次の形のコメントを Issue に残す。

  ```
  着手: <claude|codex> / ブランチ <branch> / worktree <path>
  ```

- 作業を終えたときは「完了」、途中でやめたときは「中断」のコメントで着手を閉じる。中断のときは、どこまで進んだかを書く。

## ブランチと作業ツリー

- ブランチ名は各リポジトリの既存の形（`feat/…`、`chore/…`、`docs/…` など）に合わせ、エージェント名は入れない。
- Issue 1 件につき worktree を 1 つ、`~/.worktrees/<repo>-<slug>` に作る。各リポジトリの本体の作業ツリーでは編集しない。
- 他のエージェントの worktree とブランチには書き込まず、削除もしない。
- `git stash` は使わない。stash はリポジトリ全体で共有されるので、別の worktree の作業を巻き込む。
- `git add -A` と `git add .` は使わず、変更したファイルを名前で指定する。
- push の前に `git fetch` し、同じ Issue や同じファイルを扱う PR が先に出ていないかを確かめる。出ていれば push せず、Issue にその旨を書く。

## 受け渡し

受け渡しは Issue か PR のコメントで行う。会話の文脈は他のエージェントに届かないので、コメントだけで続きに着手できる内容にする。

仕様を実装へ渡すときは、次の形で書く。

```markdown
## 仕様
- 決定:
- 根拠:
- 変更対象:
- 検証方法: (コマンドと期待値)
- リスクと未決事項:
- 次の担当: <claude|codex|人>
```

実装を終えたときは、次の形で報告する。

```markdown
## 実装の報告
- PR:
- 変更したファイル:
- 検証: (コマンドと結果。落ちたときは出力をそのまま)
- 置いた仮定:
- やらなかったこと:
- 次の担当: <claude|codex|人>
```

- 仕様の「検証方法」に ` ```verify ` の囲み（1 行 1 コマンド、終了コード 0 で成功）があれば、`agent-dispatch` が実装後にネットワークなし・HOME なしの sandbox で実行する。失敗したら Codex に最大 2 回直させ、直らなくても PR は作り、結果を報告と通知に書く。囲みがなければ「検証: 未実施」と書く。
- 次の担当が人のときは、何を判断してほしいかを 1 行で書く。
- PR のレビューは、実装しなかった側のエージェントが行う。

## Issue と PR の操作

- GitHub のリポジトリは `gh` で操作する。
- Gitea のリポジトリは `tea` で操作する。ログイン名とリポジトリの指定は、自分の環境に合わせて書く。
- `tea` のトークンが管理者のものなら、管理操作と、リポジトリの削除や設定の変更には使わない。

## ラベルによる作業の依頼

Issue または PR にラベルを付けて、作業を依頼する。ラベルごとの動作は `docs/label-workflow.md` を参照する。

- `agent:spec`: 仕様を作成して Issue にコメントする。リポジトリへの書き込みはしない。
- `agent:impl`: Issue のコメントにある仕様に従って、worktree で実装し、PR を作る。そのあと、実装していない AI がレビューする。マージは人が行う。
- `agent:pr-fix`: 利用者が作った PR のレビュー指摘を修正する。基準ブランチ以外への PR、fork からの PR、他者作成の PR は対象外にする。
- `agent:review`: 利用者が作った PR の差分をレビューして、PR にコメントする。

エージェントに渡すのは、Issue の本文とコメントのうち利用者の名義で書かれたものだけにする。外部の人の報告を依頼するときは、利用者が内容をコメントに書き直してからラベルを付ける。CI の定義（`.github/workflows/` など）を変える差分は、push せずに中断する。
