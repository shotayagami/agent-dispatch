# 検証の決まり

Claude と Codex が変更を「終わった」とする前の確かめ方。出典は Claude Code チームの記事 (https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/、2026-11-19 に読んだ) で、この環境に合わせて取り入れた部分だけを書く。

## 動かして確かめる

- 検証は変更を実際に動かすことを指す。テストが通ること、コードを読んで正しそうに見えることだけで終わりにしない。Web は Playwright MCP で、CLI やサーバーは手元で起動して、利用者が使う経路を一度通す。
- 起動と操作の手順を毎回考え直しているリポジトリでは、手順を `.claude/skills/verify/SKILL.md` に書いて残す。速く、何度実行しても同じ結果になるように保つ。
- 安い検査 (テスト、ビルド、lint) を先に通し、通ってから PR を出す。

## 直らないときは止まる

- 落ちた検査を直す試みを 3 回しても通らなければ、それ以上続けず、何が落ちているかと試したことを書いて人に渡す。agent-dispatch は検証コマンドの実行を初回を含めて 3 回で打ち切る。

## 判定の決まりを置く場所

- 変更を判定する決まり (CI の定義、レビューの観点) は、その変更が書き換えられない場所から読む。agent-dispatch は CI の定義を変える差分を push せず、REVIEW.md は基準ブランチのものを使う。
- テストを消す、skip する、期待値を書き換える、sleep や再試行を足す、のいずれかで検査を通さない。不安定なテストは原因を直す。原因が分からないときに限ってテストを消し、消した理由を PR に書く。
- レビューの結果は対象のコミットに結びつく。レビューの後に push したら、そのレビューは古いものとして扱う。

## どの検査を足すか

- 利用者の操作の流れを通す E2E テストを最優先にする。
- 「どんな入力でも成り立つ」と言える性質は property test で確かめる (Hypothesis、fast-check、proptest)。典型は往復 (encode してから decode すると元に戻る)、不変条件、冪等性 (2 回実行しても 1 回と同じ結果になる)、素朴な実装との一致である。
- 動作を変えない移行や書き換えでは、旧版と新版に同じ入力を与えて出力を比べる (differential test)。空白のように関係のない差は正規化し、意図した差は一覧にしておく。

## 記録する

- 何で確かめたかを残す。確かめていなければ「未実施」と書く。agent-dispatch はコミット本文の `Verification:` 行と実装報告に書く。
- レビューや検査が見逃した不具合は、同じ形で 2 件以上の PR に現れ、差分から見分けられるものに限って、そのリポジトリの REVIEW.md か `cross-project-lessons.md` に決まりとして足す。
- 決まりと検査は放っておくと増える一方なので、使われていないものを定期的に削る。
